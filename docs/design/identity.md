# Phase 1 · Step 1b — Identity (auth + household setup)

**Status: draft for review.** No code yet. Builds on 1a (schema + repository).

Delivers sign-in and the household/member/room/invite backend. Chores are 1c; the app
UI is 1d. This step is **backend + API only** (recommended — see decision 3).

## Auth architecture (Better Auth on Workers/D1)

The D1 binding only exists inside the request handler, so — per the current community
guidance for Workers — the auth instance is built **per request** from `env.DB`, not as
a module singleton:

```ts
// src/worker/auth.ts
export function createAuth(env: Env) {
  return betterAuth({
    database: drizzleAdapter(getDb(env.DB), { provider: 'sqlite' }),
    secret: env.BETTER_AUTH_SECRET,
    emailAndPassword: { enabled: true },
    trustedOrigins: [env.APP_ORIGIN],
  })
}
```

Mounted on Hono, with a session middleware that populates context:

```ts
app.on(['POST', 'GET'], '/api/auth/*', (c) => createAuth(c.env).handler(c.req.raw))
app.use('*', async (c, next) => {
  const session = await createAuth(c.env).api.getSession({ headers: c.req.raw.headers })
  c.set('user', session?.user ?? null)
  await next()
})
```

Better Auth **owns its own tables** (`user`, `session`, `account`, `verification`),
generated by its CLI (`@better-auth/cli generate`) into a Drizzle schema, then folded
into a `drizzle-kit generate` migration alongside ours. Our `members.userId` (added in
1a, nullable) links a household member to a Better Auth `user.id` — kept as a plain
indexed column, **not** a hard FK, so our migrations don't couple to Better Auth's
generated schema.

## Auth method — **magic link** (decided)

Passwordless email magic link via Better Auth's `magicLink` plugin. This pulls email
sending (Resend) forward into 1b. `sendMagicLink` calls the Resend REST API when
`RESEND_API_KEY` is set, and otherwise **logs the URL to the console** so local dev and
early testing work with no email at all. Resend's sandbox only delivers to your own
address until a domain is verified — enough for you to test; domain needed before
inviting others.

## Scope — **includes a minimal onboarding UI** (decided)

Introduces TanStack Router + Query now (earlier than the roadmap's 1d). Screens:
sign-in (enter email → "check your email"), create-household, and invite. The rest of
the app UI still lands in 1d.

## Secret  *(decision 2 — needs you)*

Better Auth needs `BETTER_AUTH_SECRET` (a random signing secret) as a **Worker runtime
secret**, not a GitHub Actions secret. You'll set it (I can't handle secrets):

```bash
wrangler secret put BETTER_AUTH_SECRET       # production
# and add it to .dev.vars for local dev (gitignored)
```

## New table + API (this step)

- **`invites`** table: `id`, `household_id`, `code` (unique), `email?`, `expires_at`,
  `accepted_by?`, `created_at`.
- **Endpoints** (all behind the session middleware except sign-in/up):
  - `POST /api/households` — create a household (name + IANA zone) and the caller's
    owner `member`.
  - `GET  /api/households/current` — the caller's household + members + rooms.
  - `POST /api/households/:id/invites` — owner mints an invite code.
  - `POST /api/invites/:code/accept` — join a household as a member.
  - `POST /api/rooms` · `GET /api/rooms` · `DELETE /api/rooms/:id` — room CRUD.
- **Authorization**: a `requireMember` middleware resolves the caller's member +
  household from the session and rejects non-members. One household per user for now
  (multi-household deferred, per the spec).

## Testing

Pure logic (invite-code validation, membership checks) gets unit tests. A light set of
API tests exercises the create-household → invite → accept happy path and the
non-member rejection. Auth internals are Better Auth's own concern — not re-tested.

## New dependency

`better-auth` (MIT, self-hosted, owns its tables — free at any scale). No email service
yet.
